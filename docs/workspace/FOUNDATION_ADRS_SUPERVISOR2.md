# Workspace Supervisor #2 — architecture decisions for review

**Status:** PROPOSED; not an approval or an implementation of C06/C07. **Repo baseline:** `cec6e9d0931f2e5a88a10d016603f2b85e88f113`. **Installed engine API parity:** pending; declaration pin `379a5248f09ed39c1b1734fe104b6bd73a77857f`. Owner retains final authorization. Proposed decisions below require B03/B05/B06/B07/U03 review.

## ADR-01: One semantic project and transaction owner

**Decision proposed:** The Workspace owns a versioned canonical portable Project (document, layers, assets, reusable styles, keyframes, frame collections, clips, tracks, time ranges, graph ports, binding IDs, export settings) with deterministic IDs/revisions, explicit source references, and validated atomic commands. Visual, Code, Graph, Timeline and Inspector share the same Project revision and never persist competing authoritative scene copies. Separate view state (selection, panes, zoom, scroll, playhead), durable asset bytes/references, derived compilation caches and immutable job snapshots. Unknown schema versions reject with an exportable raw recovery copy; v1 migrations must preserve all existing document fields. Commands are validated before commit, retain undo/redo history and roll back entirely upon any invalid reference, quota exceedance, graph cycle or validation error.

**Alternatives rejected:** independently editable visual/graph/code models (irreconcilable divergence); persisting native `Canvas`, `AudioContext`, `VideoFrame`, callbacks (not serializable); treating generated source as an arbitrary reversible AST (unsupported JavaScript semantics). A fully declarative JSON editor is not a substitute for main UI controls.

**Open decisions:** versioning/extension namespaces, meaningful asset identifiers and content hashes, migration of opaque future fields, IndexedDB persistence and quota recovery, conflict strategy across tabs and crash boundaries, graph node ownership, actual supported source grammar. **Verification:** migration v1->v2 data preservation, deterministic serialization, seeded IDs, stale revision rejection, transaction rollback after partial graph mutations, orphaned references, undo/redo, durable reload, malicious-prototype/oversized JSON rejection.

## ADR-02: Exact rational time, not floating-second authoritative state

**Decision proposed:** Use a portable `TimePoint = { ticks: decimalString, timebase: { numerator: positiveDecimalString, denominator: positiveDecimalString } }`, where seconds = ticks * numerator / denominator. Normalize rational values with GCD; arithmetic is BigInt internally and serializes as canonical decimal strings. `TimeSpan`/`TimeRange` follow `[start,end)` half-open semantics. An optional **default project timebase** `1/70_560_000` seconds/tick exactly represents 30000/1001, 24000/1001, 25, 30, 60 fps and common 44.1/48/96 kHz audio sample boundaries; it is not imposed on source timebases. Expose `FrameRate = {num,den}` (frames per second), distinct from tick timebase, and preserve source `PTS + timebase` (including VFR variable intervals and legal negative origins) without silently converting it to a constant-frame source.

Timing arithmetic uses normalized integer rational values with overflow-safe precision (BigInt). No conversions through JS float `Date` or `number` when producing authoritative edits. Validate decimal-string syntax/sign, nonzero denominator, GCD normalization, duration/track/frame limits and integer bit-length budget before expensive operations; cap physical workload separately. JSON contains strings so it cannot silently round values beyond `Number.MAX_SAFE_INTEGER`. Imported old floating-time settings are *not* treated as exact; migration must record explicit rational-decimal interpretation and user-visible tolerances (e.g. parse exact JSON decimal form, never binary-float expansion).

At clip split position `p`, produce `[start,p)` and `[p,end)` with source offset continuity; reject splits exactly at ends unless documented no-op. Trim and ripple use exact position deltas; no audio-to-video frame snapping except when requested. Editing scopes are frame-local/linked source/instance override/clip/range, with stable source revision and undoable copy-on-write. Audio samples retain native sample indices/rate, with resampling at explicit media boundaries; a 48,000 Hz sample is 1/48,000 s, not one 30fps frame. Seek evaluates presentation time through the same source-offset/speed/reverse mapping used in exports; stale asynchronous preview responses must be discarded by revision/playhead token.

GIF's 10ms centisecond output is a format boundary: derive integer centiseconds from **cumulative** exact rational exposure times, distributing quantization error, recording effective delays and honoring encoder minimum/maximum/disposal semantics. Never round each subframe independently without drift accounting. Fractional fps and VFR frame ranges retain original PTS externally. Tests in `timebase-adr-proposal.test.mjs` prove selected exact arithmetic only; they do not implement a shipping engine clock.

**Alternatives:** double seconds (rejected: long-range drift, frame/sample misalignment); fixed 1ms clock (reject: cannot represent 30000/1001/sample boundaries exactly); universal 90kHz clock (useful for video but not all audio sample rates); storing separate frame indices for each media domain (reject as authoritative project clock; permitted as source metadata). Universal 70.56MHz avoids many common fractions but may not cover arbitrary timebases, so retain rational timebase per source/timepoint rather than pretending all sources fit one tick grid.

**Open decisions:** one default project timebase or per-project selected rate; limits on BigInt width; rounding mode at resample/seek/encoding boundaries; exact representation of discontinuous PTS; negative source offsets; frame-duration/disposal capability; time-unit and topology exposure in codegen; migration policy for old `media.duration` floats. **Verification:** 30000/1001, 24000/1001, 44100/48000/96000, VFR PTS, negative time origins, half-open split/trim, GIF quantization, JSON roundtrip >2^53, resampling and stale seek cancellation.

## ADR-03: Engine/editor ownership and render paths

**Decision proposed:** Workspace owns edit commands, Timeline/Frame Collection UI, sessions, source-grammar reconciliation, asset browsing, view state, jobs and persistence. Apexify.js owns reusable platform-independent geometry, animation/time evaluation, paths, compiler/IR, normal rendering semantics and capability negotiation; new APIs must be proposed/versioned upstream first. Existing Node `ApexPainter` pin is audited on real installed artifact. Production realtime preview must be browser-owned retained rendering (incremental changes, resource retention, DPR, lifecycle, independent of server image encoding); Node/native executor handles bounded final GIF/WAV/video/PNG outputs. The existing PNG-on-edit route remains labeled *temporary static fallback* only. Unsupported rendering behavior raises a structured capability error; no fake API methods or silent downgrade.

**Alternatives:** extending the PNG RPC loop as realtime (rejected: per-edit network/encode/latency); bundling Node native media into browser (rejected: security/size/portability); rewriting future Apexify core inside Workspace (rejected: duplicate semantics). **Open decisions:** current `@apexify/web` entrypoint runtime parity and constraints, cross-backend tolerances, source generation for app-only helpers, detailed editor/engine ownership matrix. **Verification:** bundler dependency firewall and emitted bundle, real Chromium/Firefox/WebKit visuals, pixel/semantic delta fixture, rapid mount/unmount no leaks, invalidation and 60fps benchmark on representative hardware, API and package version matrix.

## ADR-04: No unsafe custom-program execution in Next.js

**Decision proposed:** Current public API accepts **validated declarative composition JSON only**. Arbitrary custom source is editable, downloadable and preserved, but cannot execute on the Next.js host. Any future executor requires an owner-approved separated service/container/VM with no host credentials/FS access, restricted import map, deny-by-default outbound network, CPU/wall/RSS/process/temporary-disk/output limits, termination/cancellation, scoped one-time assets, audit trails, fair anonymous quotas and response ownership. Node `vm`, `eval`, unrestricted worker threads and a shell wrapper alone are not a security boundary.

**Alternatives:** inline `eval`, `vm`, JavaScriptFunction and Node workers (rejected as isolation); strict declarative DSL only (safer fallback but cannot support arbitrary source); external sandbox service (possible subject to costs/threat model); local user-supplied runtime execution (safe for server, but weak integration). **Open decisions:** provider, image/version/patching, per-tenant identity without accounts, outbound fetch policy, abuse controls, secrets, egress logs, retention, billing, browser upload limits, job identity and leakage testing. **Verification:** malicious FS/network/process/env probes, infinite loops, memory and zip bombs, stale/cancel/race requests, cache isolation, timeouts, zero orphan processes, artifact access ownership, content-type and CSP, no host secrets in output.

## ADR-05: Git/Vercel non-deploying delivery

**Decision proposed:** Work and tests on isolated local branch/worktree; retain SHA-pinned patch/archive and commits offline. Remote pushes and PRs stay disabled until an owner-approved method is verified to generate **zero** routine Vercel previews (e.g. a dedicated disconnected mirror repo/branch with disabled integration, or project-level Deployment Protection configuration explicitly audited and approved, with a real one-off controlled proof). Never push to `main` or `studio-preview`; do not change Vercel project settings without authorization. Current `vercel.json` declares `* = false`, `main/studio-preview = true`, but historical canceled preview for a non-main branch prevents proof from config alone.

**Alternatives:** pushing ordinary feature branches and relying on `vercel.json` (rejected until empirically validated); disabling all Vercel integration unilaterally (unauthorized production settings change); delivering patch/review artifacts offline (current safe option). **Verification:** examine integration settings and recent deployment events, audit GitHub workflows, owner-approved test of one controlled no-preview delivery, non-production review release process, post-push deployment count invariant.
